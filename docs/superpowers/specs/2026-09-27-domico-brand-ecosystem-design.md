# 豆米口品牌生態與雙站行銷漏斗設計

日期：2026-09-27  
狀態：規格已於 2026-09-27 經使用者確認；實作計畫待確認

## 1. 目標

豆米口 DOMICO 是母品牌，使命是「把善意做成能被感受到的日常」。品牌同時經營兩條彼此支援、但不互相干擾的事業線：

1. `domicotaiwan.com`：小豆、小米、小口的原創 IP 世界，負責故事、角色、社群、文創商品、教育內容、授權與品牌合作。
2. `tech.domicotaiwan.com`：豆米口科技的專業服務站，負責顧問、軟體開發、AI 導入、黑客松、開班教學、企業內訓、團體與個人教練。

成功不只以瀏覽量衡量，而是看訪客是否完成下一個有意義的動作：讀完故事、找到有共鳴的角色、參與善意行動、收藏作品、提出合作需求、完成需求健檢或預約對談。

## 2. 品牌架構

- **豆米口 DOMICO**：母品牌與價值主張。
- **豆米口文創**：原創 IP、出版、商品、教育、授權與合作事業。
- **小豆・小米・小口**：豆米口創造的第一個旗艦 IP；角色擁有獨立人格、關係、矛盾、成長與長期故事，而不是公司的服務吉祥物。
- **豆米口科技 DOMICO LABS**：人本科技服務與學習事業。

「豆米口文創」保留為清楚的事業名稱；面向大眾時以角色與作品說話，不使用「幫別人製造故事」作為定位。

## 3. IP 角色與故事原則

小豆、小米、小口不設定明確年齡，讓兒童、成年人與家庭都能投射自己。每位角色都必須具有優點、缺點、矛盾與改變的可能，不被單一標籤限制。

- 真實日常負責共鳴：友情、家庭、學習、工作、失敗、孤單、期待與重新開始。
- 奇幻想像負責視覺化感受：把焦慮、勇氣、誤會或善意轉化成可看見的場景，但不取代真實問題。
- 兒童能理解事件，大人能讀到第二層意思。
- 善意不是口號或說教，而是角色在不完美的選擇中實際做出的行動。

## 4. 小豆・小米・小口 IP 行銷漏斗

### 4.1 看見

以單格漫畫、短篇動態、角色金句、生活提問與短影音切入。每個內容只承擔一個情緒，不急著推銷商品。

### 4.2 共鳴

官網用「今天的你比較像誰」與心情路徑，將訪客帶到適合的角色和故事。結果不是人格測驗標籤，而是一個當下可改變的陪伴建議。

### 4.3 追故事

漫畫依主題與故事季整理，建立角色關係、長期伏筆與成長弧。每篇提供下一篇、角色頁與相關善意行動，不形成閱讀死路。

### 4.4 參與

設計低門檻的「今日小善意」：寫一句話、分享一件小事、完成一個對身邊人的行動。內容可複製或產生分享卡，但預設不蒐集個人資料。

### 4.5 留住

訪客可收藏角色、故事與商品概念。未登入時使用本機儲存；加入 LINE 後再依主動選擇接收故事、商品、親子教育或合作資訊。

### 4.6 支持與擴散

商品以故事延伸物呈現，不用價格與促銷先壓過情感。成熟後導向預購、限定企劃、授權合作與使用者分享。教育與企業入口放在對應故事脈絡內，不以彈窗打斷閱讀。

## 5. 豆米口科技角色系統

小米是科技站的主導覽角色；小豆與小口是共同解題的伙伴。

- **偵探小米**：需求診斷、流程盤點、技術顧問。
- **建築師小米**：系統設計、網站、應用程式與軟體開發。
- **AI 副駕小米**：AI 導入、自動化、知識管理與團隊工作流。
- **隊長小米**：黑客松企劃、主持、評審機制與成果落地。
- **教練小米**：企業內訓、團體課程、個人教練與後續陪跑。

角色不是什麼都會的專家。小米會先承認未知、觀察、提問、找對方法，再和客戶一起解題。三人的方法論是：「先理解、再動手、讓人真正用得起來。」

## 6. 豆米口科技網站資訊架構

1. **首頁承諾**：把複雜的科技，變成團隊真的能使用的下一步。
2. **情境入口**：我有想法但不知道怎麼開始／系統需要開發或重整／想導入 AI／要辦黑客松／需要課程或教練。
3. **互動需求健檢**：五至七題，依目標、現況、團隊、時程與阻礙產生建議路線。
4. **服務頁**：顧問、開發、AI、黑客松、學習與教練；每頁說明適合情境、交付成果、不適合情境與下一步。
5. **方法頁**：理解、共創、實作、交接、陪跑五階段；清楚說明客戶需投入什麼。
6. **案例與證據**：初期不捏造客戶或成果。以可驗證的示範專案、方法範例、工作坊流程與實際交付物樣本建立信任。
7. **關於我們**：DOMICO 的人本科技觀、角色方法與和 IP 主站的關係。
8. **轉換區**：依意圖顯示 LINE、預約或 Email，不同場景不強迫使用者重新描述需求。

## 7. 豆米口科技行銷漏斗

### 7.1 認知

以「你的團隊不是缺 AI，而是缺一個真正用得起來的下一步」等問題型內容吸引搜尋與社群流量。首頁以情境語言取代技術清單。

### 7.2 自我辨識

訪客選擇目前處境，再完成匿名需求健檢。健檢結果包含：主要阻礙、推薦服務、第一個低風險步驟、建議準備資料。

### 7.3 建立信任

依健檢結果自動排序相關方法、示範案例、常見風險與預期交付物。每個服務頁明示不適合的客戶，避免用模糊承諾換取詢問。

### 7.4 微承諾

使用者可複製或下載需求摘要，不必先留下資料。摘要會包含其選擇、建議路線及預約前的準備清單。

### 7.5 轉換

- 低意向或單一問題：顯示 LINE 官方帳號。
- 高意向且需求清楚：顯示 Google Calendar「30 分鐘需求對焦」。
- 需要附件、規格或正式提案：顯示 `hello@domicotaiwan.com`，預填主旨與健檢摘要。
- 預約前仍不確定：先以 Email 寄出摘要，再決定是否預約。

### 7.6 交付後延伸

專案完成後導向交接訓練、團隊內訓、維運陪跑或下一階段改善；不以不透明綁約製造依賴。

## 8. 聯絡與帳號串接

### 8.1 Email

Cloudflare Email Routing 建立 `hello@domicotaiwan.com`，免費轉寄到 `domicotaiwan@gmail.com`。不在居家電腦自架郵件伺服器。網站的 Email CTA 使用結構化 `mailto:` 作為可靠的無後端備援，主旨包含服務類型，內文包含需求健檢摘要。

### 8.2 LINE 官方帳號

透過 LINE Official Account Manager 建立單一官方帳號「豆米口 DOMICO」，集中品牌好友與識別；LINE Developers Console 只用於後續 Messaging API 串接。歡迎選單分流：角色故事、商品活動、親子教育、科技諮詢、預約對談。初期網站只使用官方加好友連結與情境參數；Messaging API 待帳號建立後再綁定同一 Provider，避免提前增加機器人複雜度。

### 8.3 Google 預約

建立「30 分鐘需求對焦」Google Appointment Schedule。預約頁只在健檢結果屬於明確專案時優先顯示；其他訪客仍可從頁尾找到。初始可預約時段為週一至週五 10:00–17:00（Asia/Taipei），至少提前 24 小時，前後各保留 15 分鐘，每日最多兩場，並啟用行事曆忙碌衝突保護。網站不另存個人行程資料；實際可預約時段可由使用者隨時在 Google Calendar 調整。

## 9. 技術與部署

- IP 主站維持現有 `orsinobbb/domico-official`，由 GitHub Pages 發布到 `domicotaiwan.com`。
- 科技站建立獨立公開儲存庫 `orsinobbb/domico-tech`，以純 HTML、CSS 與 ES Modules 建置，由 GitHub Pages 發布到 `tech.domicotaiwan.com`。
- 兩站使用相對資源路徑、語意 HTML、繁體中文 SEO、Open Graph、sitemap、robots、manifest 與自訂 404。
- 無障礙基準包括鍵盤操作、清楚焦點、正確標籤、足夠對比、減少動態偏好與手機 320px 以上不水平溢位。
- 需求健檢與本機收藏以可測試的純狀態函式實作；資料預設只保存在瀏覽器，不傳送到伺服器。
- Cloudflare Tunnel 繼續服務 `studio.domicotaiwan.com → 4173` 與 `gateway.domicotaiwan.com → 3001`，但科技正式站不依賴居家電腦在線。
- `tech.domicotaiwan.com` 直接指向 GitHub Pages，不經 Tunnel。

## 10. 內容與視覺方向

IP 主站維持溫暖紙張、漫畫格與生活物件感。科技站改為較清晰的「數位工作桌」視覺：奶油白、墨黑、豆米口珊瑚色，加上小米專屬的鼠尾草綠與資訊藍。保留手寫註記和角色微動畫，但不使用廉價科幻霓虹、假儀表板或過多浮動卡片。

文案使用具體場景、交付成果與限制，避免「一站式、賦能、顛覆、全方位解決方案」等空泛詞。所有案例、數據、合作標誌與見證都必須可驗證，未取得授權前不公開客戶資訊。

科技站首版製作五張風格一致的小米角色圖，分別對應偵探、建築師、AI 副駕、隊長與教練；以現有小米造型為角色參考，每張獨立生成與檢查，不用同一張圖裁切冒充不同角色。小豆與小口只在流程協作與跨站入口中出現。

## 10.1 首版內容邊界

- IP 主站新增三人的「外在印象／內在矛盾／正在學習」角色層次、單一故事季入口、七張今日小善意卡，以及粉絲、親子教育、企業合作三條入口。
- 三則現有漫畫作為首季起點，補上角色關係與下一篇路徑；不在首版承諾尚未完成的週更頻率。
- 科技站完整呈現六類服務、五種小米任務角色、需求健檢、方法流程、示範交付物與三種聯絡轉換。
- 初期案例只使用本專案可公開驗證的官網、互動漏斗與部署實作作為示範，不虛構外部客戶。

## 11. 錯誤處理與降級

- JavaScript 失敗時仍能閱讀服務內容並使用 Email 聯絡。
- LINE 或 Google 預約尚未完成時，不顯示失效按鈕，改回 Email 路徑。
- 本機儲存不可用時，需求健檢仍能完成，但不保留進度。
- 外部連結均清楚標示目的；新視窗不作為完成任務的必要條件。
- Tunnel 或居家服務離線不影響兩個正式官網。

## 12. 測試與驗收

- 狀態單元測試：需求健檢分流、進度恢復、服務推薦、CTA 選擇與摘要生成。
- 靜態契約測試：品牌、SEO、相對資源、CNAME、manifest、robots、sitemap、404。
- 瀏覽器驗收：桌面與手機主要路徑、鍵盤操作、無水平溢位、圖片完整、無主控台錯誤。
- 發布驗收：apex、www、tech、HTTPS、Open Graph 圖、腳本與主要圖片皆回應成功。
- 串接驗收：Email 轉寄實收、LINE 加好友頁、Google 預約頁與帶有需求摘要的 Email CTA。

## 13. 實作順序

1. 建立科技站內容、角色系統與需求健檢。
2. 建立科技站 GitHub Pages 預覽並完成響應式與無障礙驗收。
3. 建立 LINE 官方帳號、Google 預約頁與 Cloudflare Email Routing。
4. 將科技站發布到 `tech.domicotaiwan.com`，驗證所有轉換入口。
5. 回到 IP 主站，依本規格補強故事季、角色成長、善意行動、教育與合作入口。
6. 建立兩站雙向導流與最終整體驗收。

## 14. 不在本階段範圍

- 自架郵件伺服器、會員帳號、付款、購物車與庫存系統。
- 未經驗證的客戶見證、合作商標或成果數據。
- 會持續收集個資的 CRM、廣告追蹤或自動推播機器人。
- 讓正式官網依賴居家主機才能瀏覽。
